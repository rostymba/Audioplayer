# Atmosphere Matching v2 — план тонкого подбора

**Статус:** Accepted (план принят), сборка по фазам
**Дата:** 8 сентября 2026
**Связано:** [audioplayer-spec.md](audioplayer-spec.md) — этот документ уточняет и частично пересматривает разделы 6.2–6.4.

## Мотивация

Нынешний подбор топорный на четырёх стыках подряд: книга → 1 из 6 словарных бакетов → 3 статичных тега → точечный поиск по фолксономии Radio Browser → скор станции, где атмосфера не участвует (HTTPS ≫ голоса ≫ битрейт). Трек (ICY `StreamTitle`) не влияет ни на что. Улучшение только парсера бесполезно: тонкость схлопывается в горлышке следующего стыка. Поэтому работаем тремя независимыми рычагами A/B/C.

## Смена природы продукта (осознанная)

С этим планом Audioplayer перестаёт быть чисто локальным демо: появляются две облачные части — (1) интерпретатор, куда улетают **вектора** книги (не текст), и (2) общее поле обучения на всех пользователей. Второе выходит за границу спеки «без серверной библиотеки». Идём на это сознательно; ранние фазы работают локально за интерфейсами, реальное облако подключается позже.

## Принятые решения

- **Приватность / вход модели (пересмотрено v2.1):** анализ полностью на устройстве. Локальная эмбеддинг-модель (EmbeddingGemma-300M / мультиязычная MiniLM через transformers.js) считает вектора прямо в браузере — ни текст, ни вектора книги не покидают устройство. Облако не участвует. Ресёрч подтвердил, что подходящая on-device модель есть, поэтому «вектора в облако» отменено в пользу полностью локального (чище по локальности).
- **Маппинг вектор → теги (пересмотрено v2.1):** отдельного облачного интерпретатора нет. Курируемый словарь тегов (`lib/atmosphere-tags.ts`, ~26 тегов с RU+EN описаниями и маппингом на теги Radio Browser) эмбеддится тем же локальным эмбеддером; матч = косинус текст↔теги (`lib/atmosphere-tagging.ts`). Это лечит нестыковку словарей и разводит разные книги по разным станциям.
- **Общее поле обучения:** «локально + интерфейс». Пишем в IndexedDB за абстракцией стора; общий бэкенд подключаем позже, не меняя логику.
- **Гранулярность профиля:** по главам (крупные главы позже можно дробить).

## Рычаг A — понимание книги

Локально: режем книгу по главам, эмбеддинг-модель → вектор на главу. Наружу — только вектора. Облачный интерпретатор возвращает многомерный профиль на главу и на книгу: жанр, настроение/валентность, энергия, эпоха/сеттинг, тяга к инструменталу, терпимость к вокалу, дуга напряжения. Считаем один раз при загрузке, кэшируем в IndexedDB. Без спойлеров: анализ всей книги при загрузке, применение — только до текущей позиции.

## Рычаг B — матчинг профиля к станциям

Вектор станции из метаданных (теги + имя + страна + язык). Подбор = косинусная близость профиль↔станции → ранжированные кандидаты. Итоговый скор — смесь доступности (HTTPS, lastcheckok, кодек, битрейт) и близости к атмосфере; нынешний «HTTPS ≫ голоса» уходит. Round-robin по странам (diversify) сохраняем.

## Рычаг C — реакция на живой трек

### C.1 Только чистые треки

Классификатор `StreamTitle`: трек / реклама / речь / джингл / **неизвестно**. Правила против дёрганья (thrashing):
- **Два действия, не путать:** приглушить внутри станции (ducking, ждать возврата музыки) vs прыгнуть на другую станцию. Реклама/речь — временное состояние → сначала ducking, а не прыжок.
- **Дебаунс:** N подряд стабильных классификаций перед действием.
- **Порог уверенности:** «неизвестно» → ничего не делаем.
- **Удержание (dwell):** быстрый скип разрешён только по рекламе/речи; атмосферный скип — редкий, под минимумом удержания (~4 мин).
- **Кулдаун** после смены.
- **Эскалация:** ducking + окно ожидания (~90 c) → если не-музыка не ушла, тогда смена станции.
- Частый опрос ICY обязателен в паре с дебаунсом и ducking, не с прыжками.

### C.1+ Тёплый резерв (promote-and-refill)

Всегда две станции: первая играет, вторая подготовлена (переиспользуем деки A/B, дек B из «включается на переход» → постоянный тёплый резерв). Неудачный старт первой или устойчивая реклама → мгновенный переход на вторую (она играет музыку, не тишину) → готовим новую вторую из пула. За деками — ранжированный пул (#3), резерв из другой страны/профиля.
**Вет резерва (добавлено):** резерв проверяется на чистоту в фоне по ICY (до 3 кандидатов, рекламные/речевые пропускаются) ещё до того, как он понадобится. Поэтому переключение по «не подходит» и по эскалации приземляется на уже проверенную музыкой станцию мгновенно и без рекламы. Плюс: на явной рекламе (высокая уверенность классификатора) приглушение срабатывает сразу, не дожидаясь дебаунса.

Режимы: **тёплый** (соединение держим, декодируем при подъёме) по умолчанию; «горячий» (играет молча, мгновенный failover, дороже по батарее/трафику) — опция под риск. Оговорки: часть станций режет второе подключение; вторая может протухнуть в рекламе (проверяем ICY в момент подъёма, за спиной пул); обе разом в рекламе — редко, спасает пул.

### C.2 Общее поле обучения

Каждый reject/skip/исход трека → общий стор на всех пользователей. Строятся глобальные предпочтения/денилист, понижающие рекламные и отвергнутые станции в подборе (замыкание с рычагом B).
**Приватный контракт:** хранить обезличенно — stationId, строка трека, ключ/корзина атмосферы, действие, время. **Не хранить** пользователя и книгу (иначе через общее поле утечёт, кто что читает).

## Открытые параметры (докрутить при сборке фаз)

- C.1 (зафиксировано, стартовые значения в `lib/radio-tuning.ts`): опрос ICY 12 с · дебаунс N=2 · окно эскалации 20 с (90 с без резерва) · кулдаун 30 с · dwell 240 с · ducking в ноль за ~1 с.
- Резерв: hot vs warm по умолчанию, мониторить ли ICY резерва, глубина пула за деками.
- A: размер окна дробления крупных глав; выбор эмбеддинг-модели.
- Метрика «стало лучше»: частота reject во времени (даёт общее поле).

## Последовательность фаз

- **Фаза 0 — сделано.** Каркас интерфейсов, doc, статусный указатель.
- **Фаза 1 — сделано.** 1a гейт чистых треков + 1b тёплый резерв + 1c общее поле (IndexedDB за абстракцией) вплетены в `RadioPanel`.
- **Фаза 2 — сделано (на стаб-эмбеддере).** `rankStations` подключён в `discover`: атмосфера участвует в скоре, сигналы общего поля понижают станции. Реальный семантический лифт — с настоящим эмбеддером в Фазе 3.
- **Фаза 3 — каркас.** Пайплайн `lib/book-analysis.ts` (главы → эмбеддинг → интерпретатор) готов и проверен на стабе; подключение к загрузке книги и реальный облачный интерпретатор (Next API-роут) — когда поднимаем облако. Со стабом поведенческого выигрыша нет, поэтому в `importEpub` пока не вшито (осознанно).
